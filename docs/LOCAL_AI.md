# Ask Bitcoin: local AI workspace

Open **Ask Bitcoin** in the sidebar, use the command palette, or navigate to `satnav://ai`. The existing galleries, wallet, exact-identifier search, sources, and advanced tools are unchanged. This integration connects the browser to a user-run LM Studio or Ollama server; it does not install an AI service, download a model, expose an inbound browser-control server, or enable MCP/plugin execution.

The [September 19 live-model/UX pass](LOCAL_AI_EXPERIENCE.md) adds shared collector statistics, exact-ID retrieval, browser-authored Rune/node summaries, restrictive per-question routing, context-window recovery, readable tables, safe inline result buttons and draft-preserving follow-ups. It also records observed model limitations and native acceptance work; general AI explanations are not verified facts.

## Connect and ask

1. Choose **LM Studio** or **Ollama**. Suggested questions only fill the composer; they never send a request automatically.
2. In your AI application, download a **chat model with tool support** and start its local server. In LM Studio, use the Developer tab and prefer a model with the tool/hammer badge. In Ollama, use a downloaded local model and disable cloud features if you want fully local inference. Keep the server bound to loopback, not your LAN.
3. Check **Local server address or port**, then select **Connect & find models**. Default addresses are `http://127.0.0.1:1234` for LM Studio and `http://127.0.0.1:11434` for Ollama. Paste the address actually shown by your server, or enter just its port, such as `11434` (expanded to `http://127.0.0.1:11434`). A `/v1` suffix is accepted and normalized. IPv6 `http://[::1]:PORT` is also supported. **Choose the app, not the port:** LM Studio can run on 11434 too. Changing the app selection preserves a custom address.
4. Progress, **Cancel connection**, and actionable errors appear beside Connect. A successful check selects a model; LM Studio model-type metadata excludes embeddings and prioritizes already-loaded models when available. **Server connected** means discovery succeeded, not that inference or tool use has been proven. **Model responded** appears after a usable reply/tool result. The status tooltip gives the model count, whether inference has been tested and the check time; availability is rechecked for each question, not by background port scans.
5. Ask your question and select **Ask Bitcoin**, or press **Enter**. **Shift+Enter** adds a newline; IME composition cannot accidentally submit an unfinished question. The **Bitcoin data** toggle (accessible name: “Allow read-only Bitcoin lookups”) is visible beside Send. With it off, the model can explain concepts but receives no tools and cannot request source data.

The chat uses one centered conversation column, right-aligned user messages, formatted replies, inline Bitcoin cards and a bottom composer. Starter questions disappear after the first message. Answers support short headings, lists, emphasis, code and semantic tables without interpreting HTML, images or executable content. Exact references to existing validated cards may become user-operated result buttons; unmatched model links and arbitrary URLs remain inert. Source details, additional cards and lookup activity expand on demand; Copy answer is an explicit clipboard action. Earlier answers keep their own cards, not a single shared results panel. Connection, selected model, draft, transcript position and expanded disclosures survive normal sidebar return. Follow-up suggestions fill the composer without sending, and an overwritten unsent draft can be restored.

The workspace has **one vertical content scroll area**, with the model/connection header and composer anchored outside it. The transcript no longer scrolls inside a scrolling page. Setup, answers, cards and privacy details share that scroll area. Reading older content pauses automatic following; **Jump to latest** returns to the newest answer and focuses the composer. Returning from a result preserves both the position and paused-following state. Connection setup opens at the top of the same area; closing it returns to the previous position. Narrow/short windows compact the layout without removing chat or connection controls. A long editable prompt can still scroll within its text input; wide code examples can scroll horizontally.

LM Studio API tokens are optional, entered by the user under Connection options, and retained only in memory for this tab's session. They are never loaded from environment variables, files, or Keychain and never stored in preferences. Disconnecting or closing the tab discards the token. The browser never turns off server authentication. Connection/server/model changes start a new chat to avoid silently sending earlier messages to a different model/server.

If a reachable server does not return the expected model list, check the selected app and address. If the window reports that the AI connection service is unavailable, restart Bitcoin Browser to load matching main-process and renderer code. Connection diagnostics retain only capped, fixed success/error codes—never addresses, model names, server responses, questions, answers, or API tokens.

Official setup/API references: [LM Studio server](https://lmstudio.ai/docs/developer/core/server), [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools), [LM Studio model metadata](https://lmstudio.ai/docs/developer/rest/endpoints), [Ollama quickstart](https://docs.ollama.com/quickstart), [Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling), [Ollama compatibility API](https://docs.ollama.com/api/openai-compatibility), and [Ollama local-only/cloud settings](https://docs.ollama.com/faq).

## What the AI can find

| Tool | Scope | Result |
| --- | --- | --- |
| `get_bitcoin_sources` | Enabled, eligible sources for the selected network | Source names, types, local/public classification, capabilities and last-known health; no active probe or credential/configuration dump |
| `get_bitcoin_status` | Chain/node sync, mempool or fee estimates | A source-labeled status card; Core uses fixed `getblockchaininfo`, `getmempoolinfo` and `estimatesmartfee` calls, Ord supplies indexed height, explorers supply supported status/fee data |
| `lookup_bitcoin` | Exact block height/hash, transaction ID, public address, output, inscription ID/number, sat, satpoint, or Rune name/ID | Card plus bounded record details: paginated transaction inputs/outputs or block transaction IDs, address confirmed/pending statistics, output inscriptions/Rune balances, inscription metadata, Rune supply/mint terms, sat details and related native identifiers |
| `read_inscription` | Exact inscription ID | Up to 6,000 characters of inert text/JSON/HTML/SVG content per excerpt; pagination, MIME, decoded byte size and source provenance; no content execution or binary-media inspection |
| `find_recursive_inscriptions` | Three exact mainnet examples linked from the Ordinal Handbook | Inspects actual content and returns openable artwork cards, ordered only by observed references within this sample; no network-wide ranking |
| `inspect_inscription_recursion` | One exact inscription ID or number | Resolves numbers through Ord, traverses bounded content references and validated sat-at-index pointers, and reports sources, counts, observed hops, unresolved reads and scan limits |
| `get_ord_relationships` | Parents/children of an inscription or inscriptions on a sat | Up to 12 validated IDs per excerpt, source-page and excerpt pagination, source-labeled openable cards; provenance is not content-recursion depth |
| `browse_inscriptions` | A bounded Ord listing page, optionally within a block | Up to 12 example cards and a button to open the full browser listing |
| `browse_runes` | A bounded Ord listing page | Up to 12 Rune cards and a button to continue browsing |
| `search_featured` | The bundled mainnet-only editorial Rune/inscription catalog | Exact native targets, editorial context, and an explicit curated-example label |

Try “Which Bitcoin sources can you use?”, “Check my local Core sync status”, “Find DOG and explain its mint terms”, “Read the text in this inscription”, or “Explain the inputs and outputs of this transaction”. Paste a public identifier to research a specific entity. These are lookups, not wallet connections. Address confirmed and pending statistics are separate source snapshots, not spendable balances or a complete wallet. Core BTC values and explorer satoshi values are normalized separately; Rune integer base units and divisibility remain exact.

The model may choose and chain relevant tools on each question. Clear, direct recursive find/inspect requests also have a browser-owned action-first path described below. It can request `source: "local"` to prohibit public fallback, and an optional `service` filter (`bitcoin-core`, `ord-server`, `mempool`) to select an existing service type without falling back to another type. Omission uses normal browser preferences and fallback. Neither selection can enable a service, bypass network/offline/local-only settings, change a URL or inspect credentials. Core is not a general address/Ord index; a syncing or pruned node, missing `txindex`, and missing Ord indexes may prevent particular reads. The app does not secretly install or start services to complete a question.

**Bitcoin results** belong to the browser, not the model. Inline cards display source names, networks, fetch/review times, cache labels, facts and curated-versus-source distinctions. Four cards are shown initially; additional cards and full source facts are disclosed on demand. The model cannot manufacture interactive cards or arbitrary links. Select **Open in browser** to open an exact entity in a new normal tab; status-only cards intentionally have no invented destination. Lookup activity shows actual tool stages and their source names, never hidden model reasoning. Earlier answers retain their cards and the composer remains stable during passive updates. Switching Bitcoin networks starts a new chat, and result buttons independently check their network before opening.

To return from an inscription or other result, select **Ask Bitcoin in the sidebar** (or its command-palette entry). This resumes your existing AI tab with its connection, selected model, conversation, unsent draft and result cards; it does not create a blank chat in the result tab or automatically reconnect/send a question. The result tab stays open. If you intentionally use multiple AI tabs, the current tab's retained session takes priority, otherwise the most recently visited open session is resumed. A session can also be resumed after its owner browsed elsewhere in-place. Explicitly closing its tab or restarting the browser still clears that memory-only conversation; the next question rechecks server availability as before.

The catalog is not a global collection-name/content-keyword index, a popularity ranking, or a price feed. Listings are samples in source-defined order, not exhaustive or ranked search. There is no live market-price, portfolio, transaction-broadcast, wallet-signing, or arbitrary web-search tool. Missing fields remain unknown, not zero. AI explanations can still be wrong; verify important claims against the actual source details.

## Finding recursive inscriptions

Use the **Find recursive art** starter, or ask **“Find a highly recursive inscription.”** With Bitcoin data enabled, a narrow main-process intent handler performs the search even if the selected model would otherwise respond from memory with a tutorial. The answer is explicitly labeled **Browser-generated lookup summary**, with actual inspection activity and openable result cards. It still checks the selected server/model catalog, but does not falsely mark model inference as tested. Explanation-only, multi-target and more complex requests remain model-led for tool selection; both recursion tools are available to the model. Once a recursion tool is used, its factual summary is also browser-generated: model prose cannot replace the measured counts with invented ancestry, longest-path claims or unsupported network comparisons. Multiple inspections retain each result; other tool cards and activity remain available. Successful Rune statistics, direct local-node status checks and fully unsuccessful lookup responses also have browser-authored summaries, as described in the experience report. General conceptual chat remains model-generated. This is not a general natural-language parser or a guarantee against every model hallucination.

The protocol distinction matters: [Ord recursion](https://docs.ordinals.com/inscriptions/recursion.html) means content can load other inscriptions or allowed on-chain data. [Parent/child provenance](https://docs.ordinals.com/inscriptions/provenance.html) is a separate explicit relationship, not automatic UTXO ancestry; [multiple parents are supported](https://github.com/ordinals/ord/pull/3227). Bitcoin Core does not supply an Ord index or a recursive-inscription search RPC. An inscription number is resolved to its transaction-based ID before reading content. No invented `/inscriptions/NUMBER/children` endpoint is used. Core-only requests explain the missing Ord capability instead of querying an unrelated RPC or silently choosing a public source.

The finder starts from these actual works, reviewed against the [Handbook examples](https://docs.ordinals.com/inscriptions/examples.html) on 2026-09-12:

- Oscillations: `52b4ea10c2518c954c73594e403ccfb2d50044f5a3b09a224dfa3bf06dd1d499i0`.
- Blob #1: `b10b00bfb146fee3e86d6cbd8e8c954c485da41be480c0b21a6a63de7986892bi0`.
- Chordinals: `aa43e0a7d229f460c6f9310e938ae8ec50a26f5b09df1f6d801d9e8a8741afc3i0`.

These are a small curated candidate set, not presumed inspection results. Cards appear only after source content is successfully read and references observed. Results open the artwork itself, not a shared renderer that might lack the artwork's metadata. Non-mainnet requests require an exact inscription on that network; the mainnet seeds are not sent to another network's source.

The inspector reads inert text through the browser's existing Ord resolver and cache. It recognizes whole root-relative or `ord://` content literals, selected data-endpoint literals, and simple sat templates such as a single `const sat = DECIMAL;` used in `/r/sat/${sat}/at/-1`. Only exact content IDs and range-checked `/r/sat/NUMBER/at/INDEX` pointers can cause further reads; returned pointer IDs are validated. Sat indices are bounded to signed 32-bit magnitude and sat numbers below [Ord's total supply](https://github.com/ordinals/ord/blob/master/crates/ordinals/src/sat.rs). Other referenced data endpoints are reported, not fetched. Parents/children arrays and bare inscription IDs do not become content edges. External URLs, arbitrary paths, expressions, script execution, general template evaluation and arbitrary RPC are unavailable.

Counts are observations, not an execution trace: comments or unused literals can be counted, dynamically constructed/encoded references can be missed, Ord can serve delegated content, and sat pointers can change. Observed hops describe the bounded breadth-first traversal, including sat-pointer edges, **not** the longest possible graph path or parent/child depth. Unreadable, unavailable, oversized and out-of-budget dependencies are disclosed. Missing static references do not prove an inscription is nonrecursive. There is no protocol-defined “highly recursive” threshold or claim to find the most recursive inscription on Bitcoin.

One scan is capped at **36 unique resource attempts, five traversal hops, 64 references per text resource, 1 MiB per content resource, 128 KiB per sat-pointer reply, a 4 MiB accounted aggregate byte budget, 10 seconds per resolver request and 45 seconds total**. Smaller user graph/resource limits take precedence. Both wire and decompressed bytes are bounded; failures are charged conservatively. Existing source fallback may involve multiple transport attempts for one resource. All candidate roots are visited before descendants, shared dependencies are fetched once, and cycles terminate. Model detail exposes at most 12 dependency IDs and six endpoint examples per result, followed by the existing overall model-context limits.

Local-only and service restrictions apply to the complete traversal and its cache partition. Offline mode uses only eligible cached entries and exposes cache/stale labels. An explicit offline request when Offline mode is off stops with guidance instead of doing online inscription reads. Routing changes, user cancellation and shutdown invalidate the scan; an inspection deadline can return clearly labeled partial evidence. No source is installed, enabled or reconfigured, and no wallet or credential authority is added.

## Privacy and authority boundaries

- AI networking is main-process-only. The app renderer cannot directly fetch arbitrary AI endpoints, and no CSP, sandbox, wallet partition, web permission or inscription authority is widened.
- Endpoints must be literal loopback HTTP addresses on ports 1024–65535. `localhost` becomes `127.0.0.1` before transport. LAN addresses, noncanonical IP spellings, embedded credentials, arbitrary paths, query strings and fragments are rejected. Only fixed model-list and completion paths are used. Redirects are denied, the exact origin is pinned, and there are no cookies or ambient/proxy credentials.
- Model discovery uses Ollama `/api/tags`, or LM Studio `/api/v0/models` with a narrowly scoped `/v1/models` compatibility fallback when unsupported. Generation uses `/v1/chat/completions`, `stream: false`, a fixed output budget and explicit function schemas. Nothing invokes server-side MCP, web-search, model-download/load/unload, arbitrary code or filesystem APIs.
- Ollama entries advertising `remote_host`, `remote_model`, or conventional cloud model IDs are excluded and the catalog is rechecked each turn. **A loopback endpoint is not proof of local inference**: a server can proxy requests or misreport metadata. The user must choose trusted downloaded models and disable remote routing; server-side retention is outside Bitcoin Browser's control.
- Only this chat's recent user/assistant messages, a bounded list of previously displayed native result references and the requested bounded Bitcoin data are sent to the chosen server. Source discovery exposes enabled source names/types/capabilities, not URLs, IDs, credentials, cookie paths or configuration. No automatic open-page, browser-history, bookmark, wallet, private-key, credential, file or environment context is collected. Never paste secrets into chat.
- Only user/assistant roles are accepted from the renderer. Model tool calls are parsed as data, validated against the closed allowlist, and invoked through explicit branches. The model is not granted a provider object, generic RPC, URL fetch, shell, or navigation function. Tool text is treated as untrusted data, and output is rendered with text nodes, never HTML, arbitrary Markdown navigation, scripts or frames. A reference matching an existing validated result card can receive a user-operated button; its exact target and network are independently checked before navigation.
- Bitcoin entities and status use the existing ProviderManager; inscription text/relationships use the existing RecursiveResolver and bounded decompression. Selected-network, local-only, offline/cache, routing-invalidation, provider capability and shutdown ownership still apply. Explicit local/service-filtered recursive reads have distinct cache partitions; strict entity-cache reads require recorded source locality/type as well as an eligible provider identity. Legacy cache entries lacking that metadata may need a normal online refresh before they satisfy a strict offline query. Live network status is not fetched offline. Public identifiers can reach configured public sources when enabled. Local AI does not imply local Bitcoin data. Existing app-managed Core authentication is used internally, never supplied to the model. Normal provider-cache and lookup-failure logging rules apply to those public identifiers; chat text and AI API tokens are not added to logs.
- The four AI IPC channels (`ai:prepare`, `ai:run`, `ai:progress`, `ai:cancel`) require the trusted, current main application document. Main-issued one-use handles retain ownership through cancellation, frame destruction and actual transport settlement. Progress returns only a browser-produced projection, not the prepared prompt/token/config. Inscription/wallet frames cannot call these channels.
- Browser-side chat storage is memory-only: up to 20 turns per tab, with at most eight recent completed user/assistant messages and 24,000 characters sent as context. Closing a tab/browser, disconnecting, or starting a new chat clears the corresponding conversation. Ordinary OS memory/swap and the AI server's own logs are not controlled by this feature. Only provider/address/model preferences persist.

## Bounds and recovery

Each question permits at most ten tool calls across seven generation rounds, with 24 result cards, a 4,000-character prompt, 12,000-character answer, 1 MiB per AI response and up to 1,536 generated tokens per completion (1,024 for reported contexts below 8,192). Loaded-context budgeting may shorten complete older history/tool groups or detail excerpts without removing the current question or visible UI; shortening and server context-limit errors are disclosed. Tool context is also capped at 12,000 characters per result and 32,000 cumulatively. Entity reads cap transport at 8 MiB or the user's smaller browser limit; record lists expose 12 items at a time. Text content is capped at 256 KiB on both encoded and decoded bytes, with 6,000-character excerpts. Ord relationship replies are capped at 128 KiB and 100 IDs per source page. Unsupported/oversized binary content remains a browser-viewing task, not a model input. No raw scripts, witnesses or entire entity bodies are dumped into model context.

Model lists are bounded to 200 entries. There are at most four prepared requests and two active AI operations; idle preparations expire after 15 seconds. Model-list reads have 10-second transport deadlines, inference calls have 120-second deadlines, and the whole chat turn has a 240-second limit. Live status tries at most three eligible providers with bounded read-only calls. Existing provider/cache limits and routing cancellation remain in force.

Requests show stage-level progress (checking server, thinking, looking up, explaining). This beta returns complete text messages, not token-by-token streaming. Progress polling is nonoverlapping and stops on completion/disposal. **Stop** works during connection preparation, inference and Bitcoin lookups. Navigating away stops active AI work and retains already-completed chat/results; late replies cannot overwrite the new view. The browser aborts transports but cannot guarantee that every third-party server immediately releases its GPU work.

Source failures remain visible. When no checked cards exist, unsuccessful reads cannot be replaced with a model's fabricated live-data answer; editorial examples remain explicitly editorial. If summarization fails after a successful lookup, completed cards remain usable. **Edit & try again** restores the question but never auto-replays it. Models that do not support tools can be used with lookups off; choose a tool-capable model for search. Model memory and context capacity vary: larger chats/listings may require a larger configured context window, a shorter question, or a new chat. The browser does not silently alter server context/GPU settings.

## Verification and manual acceptance

`tests/local-ai.test.js` covers transport/API contracts, real loopback HTTP fixtures for both servers, redirect/socket/body limits, strict schemas, model metadata, state preference persistence, projections, duplicate/budget handling, cancellation and routing/shutdown invalidation. `tests/local-ai-data.test.js` covers provider eligibility/service filters, projections, unit normalization, paginated content/relationships, cache provenance and decompression bounds. `tests/local-ai-recursion.test.js` covers static graphs, sat indirection, source restrictions, cancellation and grounded recursion answers. `tests/local-ai-experience.test.js` adds collector projections, exact/canonical targets, actual Core status, grounded Rune answers, safe failure summaries, question policies and loaded-context fitting. `tests/local-ai-ipc.test.js` exercises the real preload, IPC registration and document-owned registry. `tests/local-ai-ui.test.js` runs actual view/request handlers with a bounded DOM collaborator, including inert tables, exact-card inline buttons, draft restoration, keyboard input, retained scroll/disclosures and sidebar lifecycle. All six suites are included in `npm run security:beta` and the full test suite.

Expanded-tools live test on 2026-09-12: the already-running LM Studio `openai/gpt-oss-20b` completed source discovery → strict-local Core status → a correctly formatted explanation in **4.3 seconds**. The actual LocalAiManager/model transport and actual Core health adapter were used, but Core RPC responses were **synthetic fixtures** (height 100, headers 101, 95% progress, pruned, initial download). The only selected RPC was `getblockchaininfo`; no real node, credentials, user conversation or wallet was read. This proves a real model/tool round trip, not real-node synchronization or native UI fidelity.

Recursive-search live checks on 2026-09-12 used production LocalAiManager, ProviderManager and RecursiveResolver, real public Ordinals.com content and the existing LM Studio `openai/gpt-oss-20b` catalog/model. Settings were synthetic and cache storage was in memory, not the user's profile. The three-candidate action-first search completed in **2.3 seconds**, observing **42 content references for Blob #1**, **11 for Oscillations** and **7 for Chordinals**, with explicit partial-scan limits for Blob. The final model-led exact Blob inspection selected `inspect_inscription_recursion` and returned the browser-grounded summary in **13.0 seconds**: **56 distinct content references, five observed traversal hops, 36 resources read and 22 unresolved content references**. A single-target scan has more of the shared resource budget than a three-candidate scan; the differing counts are bounded observations, not contradictory network-wide totals. No inscription code was executed or native artwork rendering qualified. Earlier model-led trials misinterpreted hop counts and invented typical-inscription comparisons despite prompt guidance; the final implementation deliberately prevents model prose from replacing measured recursion summaries. General model answers outside this workflow can still be wrong.

The implementation uses the documented [Core mempool RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getmempoolinfo/), [Core fee estimation RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/util/estimatesmartfee/), [Ord recursive endpoints](https://docs.ordinals.com/inscriptions/recursion.html), and existing explorer adapters. The browser does not provide an unrestricted RPC/API console to a model.

Live test on 2026-09-12: existing LM Studio at `127.0.0.1:11434`, already-loaded `openai/gpt-oss-20b`, completed a real curated Runestone tool round trip in approximately **2.7 seconds**, producing the exact inscription card and an appropriate explanation. A separate live block-840000 query exercised tool use but the public `mempool.space` source timed out; the model correctly reported unavailable data. A direct bounded provider lookup independently reproduced that timeout. No server configuration, model installation, credentials, profile history or wallet state was read/modified. This is not real-Ollama inference qualification; its API is covered by fixtures.

Before beta sign-off, test the native layout at narrow/wide sizes and in dark/light mode, keyboard navigation and a screen reader, the final packaged build on each OS/architecture, a real downloaded Ollama model, LM Studio token-enabled operation, slow/cold and low-context models, disconnect/reconnect, and live entities from each supported Bitcoin source. Native fixed readiness markers contain only state/PID and demonstrate that the view mounted, not visual fidelity or real-model correctness. These feature checks do not clear the broader project beta release gates or guarantee third-party wallet/model-server safety.
